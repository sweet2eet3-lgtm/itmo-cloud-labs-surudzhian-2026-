# Лабораторная работа №2. Исследование Cloud Run

## 1. Цель работы

Ознакомиться с возможностями сервиса Google Cloud Run, изучить процесс развёртывания контейнеризированных приложений, мониторинга их работы, управления версиями и распределения трафика.

## 2. Ход работы

### 2.1. Создание сервиса Cloud Run

В учебном проекте Google Cloud `cloud-platforms-as-the-basis` был открыт раздел Cloud Run.

Для развёртывания выбран готовый контейнер **Hello** с помощью функции `Test with a sample container`.

Сервис был создан со следующими параметрами:

| Параметр | Значение |
|---|---|
| Service name | `asurudzhian-run-lab2` |
| Region | `europe-west1` (Belgium) |
| Container image | `us-docker.pkg.dev/cloudrun/container/hello` |
| CPU | 1 vCPU |
| Memory | 512 MiB |
| Minimum instances | 0 |
| Maximum instances | 1 |
| Billing | Request-based |
| Ingress | All |
| Container port | 8080 |

Использование минимального количества экземпляров `0` позволяет автоматически останавливать вычислительные ресурсы при отсутствии запросов.

После создания сервис получил статус Ready.

Была автоматически создана первая ревизия:

`asurudzhian-run-lab2-00001-w92`

На неё направлялось 100% входящего трафика.

### 2.2. Тестирование сервиса

После успешного развёртывания был открыт публичный URL сервиса:

`https://asurudzhian-run-lab2-307056602443.europe-west1.run.app`

В браузере отобразилась стандартная страница Cloud Run с сообщением:

`It's running!`

Таким образом, была подтверждена работоспособность контейнеризированного приложения и доступность сервиса по HTTP.

### 2.3. Анализ логов

Для анализа работы приложения выполнен переход в раздел **Observability → Logs**.

В журналах были обнаружены следующие события:

- Создание сервиса Cloud Run.
- Запуск нового экземпляра контейнера.
- Успешный запуск контейнера на порту `8080`.
- Успешное прохождение стартовой TCP-проверки.
- HTTP-запросы `GET` со статусом `200 OK`.

Время обработки отдельных запросов в журнале составляло приблизительно 4–15 мс.

Ошибок при первоначальном запуске и тестировании сервиса обнаружено не было.

### 2.4. Анализ метрик

В разделе **Observability → Metrics** были изучены основные показатели работы Cloud Run.

Рассмотрены:

- **Request count** — количество поступающих запросов.
- **Request latencies** — задержки обработки запросов.
- **End-to-end request latency** — общее время выполнения запроса.
- **Latency breakdown** — составляющие задержки.

На графиках были зафиксированы успешные запросы со статусами `2xx`.

Задержки обработки запросов составляли приблизительно 12–16 мс по графику Request latencies, а полная задержка запроса — около 25–35 мс.

Небольшое количество точек на графиках объясняется низкой нагрузкой на тестовый сервис.

### 2.5. Изменение порта контейнера

Для исследования изменения конфигурации Cloud Run был выполнен переход в раздел **Containers**.

Порт контейнера был изменён:

- **Первоначальный порт:** `8080`
- **Новый порт:** `8090`

После изменения настроек выполнено развёртывание новой ревизии с помощью команды **Redeploy → Deploy changes**.

В результате была создана вторая ревизия:

`asurudzhian-run-lab2-00002-j6r`

После обновления трафик распределялся следующим образом:

| Ревизия | Порт | Трафик |
|---|---|---|
| `00001-w92` | 8080 | 0% |
| `00002-j6r` | 8090 | 100% |

После перехода по URL сервиса повторно отобразилась страница `It's running!`.

На странице была указана новая ревизия `00002-j6r`.

Следовательно, изменение порта с `8080` на `8090` не нарушило работоспособность стандартного контейнера Hello. Приложение продолжило успешно принимать HTTP-запросы.

### 2.6. Переключение трафика между ревизиями

Для проверки возможностей управления версиями был открыт раздел **Revision History → Manage traffic**.

Первоначально 100% трафика направлялось на вторую ревизию `00002-j6r`.

Затем была выбрана настройка **Send all traffic to one revision**, после чего весь трафик перенаправлен на первоначальную ревизию `00001-w92`.

Итоговое распределение:

| Ревизия | Порт | Трафик |
|---|---|---|
| `00001-w92` | 8080 | 100% |
| `00002-j6r` | 8090 | 0% |

Переключение завершилось успешно.

Эксперимент продемонстрировал возможность управления распределением пользовательских запросов между различными версиями одного приложения.

Такой механизм позволяет возвращать пользователей на предыдущую стабильную версию приложения без повторного создания сервиса.

### 2.7. Удаление созданных ресурсов

После завершения эксперимента сервис `asurudzhian-run-lab2` был удалён через Google Cloud Console.

Удаление выполнено для освобождения облачных ресурсов и предотвращения дальнейшего потребления ресурсов учебного проекта.

## 3. Вывод

В ходе лабораторной работы были изучены основные возможности Google Cloud Run.

Был успешно развёрнут контейнеризированный сервис Hello с минимальными вычислительными ресурсами.

Проверена доступность приложения по публичному URL, исследованы журналы событий и метрики производительности.

Изменение порта контейнера с `8080` на `8090` привело к созданию новой ревизии, при этом приложение сохранило работоспособность.

Дополнительно было успешно выполнено переключение 100% трафика между двумя ревизиями.

Cloud Run позволяет развёртывать контейнеризированные приложения без самостоятельного управления серверами, автоматически масштабировать их и управлять версиями приложения.

После завершения работы созданный сервис был удалён.

**Цель лабораторной работы достигнута.**
