# Лабораторная работа №4. Разработка инфраструктуры MVP AI-приложения

## 1. Цель работы

Разработать инфраструктуру прототипа AI-приложения, определить необходимые облачные сервисы для трёх этапов развития продукта, рассчитать предполагаемые расходы и обосновать выбор архитектурных решений.

## 2. Описание приложения

Для лабораторной работы разработана концепция **AI English Helper** — веб-приложения для изучения английского языка с использованием искусственного интеллекта.

Пользователь вводит английское слово, выражение или предложение, а приложение предоставляет:

- Перевод на русский язык.
- Объяснение значения простым английским.
- Пример использования в предложении.
- Возможность сохранять историю запросов на последующих этапах развития.

Для генерации ответов используется Gemini 2.5 Flash-Lite API.

Приложение не требует обучения собственной AI-модели, что снижает расходы на запуск и техническую сложность проекта.

## 3. Проектирование инфраструктуры

Для приложения предусмотрены три этапа развития: начальное MVP, тестирование партнёрами и полноценная эксплуатация (Production).

### 3.1. Этап 1 — MVP

На первом этапе предполагается 100 пользователей.

Инфраструктура состоит из:

- **Веб-интерфейса** — взаимодействие с пользователем.
- **Google Cloud Run** — размещение серверной логики и обработка запросов.
- **Gemini AI API** — генерация переводов и объяснений.

Принцип работы:

1. Пользователь отправляет текст через веб-интерфейс.
2. Запрос поступает в приложение, размещённое на Cloud Run.
3. Сервер обращается к Gemini AI API.
4. AI генерирует объяснение.
5. Ответ возвращается пользователю.

На данном этапе не используется отдельная база данных, поскольку хранение истории запросов не является обязательным для проверки основной гипотезы продукта.

Для Cloud Run предполагается конфигурация:

| Параметр | Значение |
|---|---|
| CPU | 1 vCPU |
| Memory | 512 MiB |
| Minimum instances | 0 |
| Billing | Request-based |
| Scaling | Automatic |

**Обоснование:** Cloud Run позволяет запускать контейнерное приложение без управления виртуальными машинами и масштабировать его до нуля при отсутствии запросов.

### 3.2. Этап 2 — Тестирование партнёрами

На втором этапе предполагается увеличение аудитории до 1 000 пользователей.

К существующей инфраструктуре добавляются:

- **Cloud Firestore** — хранение пользовательских данных и истории запросов.
- **Cloud Logging** — сбор и анализ журналов работы приложения.

Обновлённая архитектура:

1. Пользователь обращается к веб-интерфейсу.
2. Cloud Run обрабатывает запрос.
3. Gemini AI API генерирует ответ.
4. Firestore сохраняет необходимые данные запроса и историю.
5. Cloud Logging собирает технические события.

**Обоснование:** Firestore является управляемой NoSQL-базой данных, не требующей самостоятельного администрирования серверов.

Cloud Logging позволяет обнаруживать ошибки, анализировать работу приложения и исследовать поведение системы во время тестирования.

На данном этапе сохраняется Cloud Run, поскольку его автоматическое масштабирование позволяет поддерживать увеличивающуюся нагрузку без перехода на более сложную инфраструктуру.

### 3.3. Этап 3 — Production

На третьем этапе предполагается 10 000 пользователей.

В архитектуру добавляются:

- **Cloud Monitoring** — контроль производительности и состояния инфраструктуры.
- **Secret Manager** — безопасное хранение API-ключей и других секретов.

Итоговая инфраструктура:

- Веб-интерфейс.
- Google Cloud Run.
- Gemini AI API.
- Cloud Firestore.
- Cloud Logging.
- Cloud Monitoring.
- Secret Manager.

Cloud Run автоматически увеличивает количество экземпляров приложения в зависимости от входящего трафика.

Firestore обеспечивает хранение пользовательских данных, а Cloud Monitoring позволяет отслеживать ключевые технические показатели.

Secret Manager используется для исключения хранения API-ключей непосредственно в исходном коде.

Для повышения надёжности рекомендуется также использовать ограничение частоты запросов, аутентификацию пользователей и резервное копирование важных данных.

**Обоснование:** выбранная архитектура позволяет масштабировать продукт без перехода на Kubernetes или самостоятельное управление серверами. Это уменьшает операционную сложность и затраты небольшой команды.

## 4. Экономическая модель

### 4.1. Исходные допущения

Для расчёта приняты следующие параметры:

| Параметр | MVP | Partners | Production |
|---|---:|---:|---:|
| Пользователи | 100 | 1 000 | 10 000 |
| AI-запросов на пользователя в месяц | 30 | 30 | 30 |
| AI-запросов за месяц | 3 000 | 30 000 | 300 000 |
| Входных токенов на запрос | 500 | 500 | 500 |
| Выходных токенов на запрос | 300 | 300 | 300 |
| Расчётное время Cloud Run на запрос | 2 с | 2 с | 2 с |

Приведённые значения являются сценарными допущениями для учебного проекта.

Для расчёта используется Gemini 2.5 Flash-Lite со следующими тарифами стандартного платного API:

- Входные токены — $0.10 за 1 млн.
- Выходные токены — $0.40 за 1 млн.

### 4.2. Расходы на AI

Стоимость одного запроса рассчитывается по формуле:

`C = (500 × 0.10 + 300 × 0.40) / 1 000 000`

Результат:

`C = $0.00017`

Месячные расходы:

| Этап | Запросов | Стоимость |
|---|---:|---:|
| MVP | 3 000 | $0.51 |
| Partners | 30 000 | $5.10 |
| Production | 300 000 | $51.00 |

Таким образом, при выбранной модели затраты на AI увеличиваются пропорционально числу запросов.

### 4.3. Расходы на Cloud Run

Для оценки используется модель Request-based billing.

Основные параметры расчёта:

- 1 vCPU.
- 512 MiB оперативной памяти.
- 2 секунды оплачиваемой работы контейнера на запрос.
- Минимальное количество экземпляров — 0.
- Бесплатная квота CPU — 180 000 vCPU-секунд в месяц.
- Бесплатная квота памяти — 360 000 GiB-секунд в месяц.
- Бесплатная квота запросов — 2 млн в месяц.

Расход CPU:

| Этап | vCPU-секунд в месяц |
|---|---:|
| MVP | 6 000 |
| Partners | 60 000 |
| Production | 600 000 |

На первых двух этапах предполагаемая нагрузка укладывается в бесплатную квоту.

На этапе Production расчётное превышение квоты CPU составляет:

`600 000 − 180 000 = 420 000 vCPU-секунд`

При ориентировочной ставке $0.000024 за vCPU-секунду:

`420 000 × 0.000024 = $10.08`

Расход памяти на этапе Production составляет 300 000 GiB-секунд и в принятой модели укладывается в бесплатную квоту.

Количество запросов также остаётся ниже бесплатного лимита.

**Оценочные расходы на Cloud Run:**

- MVP — $0.
- Partners — $0.
- Production — $10.08.

Расчёт использует базовые тарифные ориентиры и предполагает, что бесплатные квоты доступны проекту в полном объёме. Фактическая стоимость зависит от региона, нагрузки и использования квот другими проектами того же платёжного аккаунта.

### 4.4. Остальные сервисы

**Cloud Firestore**

Для модели предполагается одна запись и две операции чтения на AI-запрос. Суточная нагрузка при равномерном распределении запросов не превышает бесплатные квоты 20 000 записей и 50 000 чтений в день даже на этапе Production.

Также предполагается, что объём данных не превышает бесплатный 1 GiB.

Расходы в рамках этих допущений — $0.

**Cloud Logging**

Для проекта предполагается объём журналов меньше бесплатного лимита 50 GiB в месяц. Срок хранения не превышает стандартные 30 дней.

Расходы — $0.

**Cloud Monitoring**

Предполагается использование стандартных метрик Google Cloud Run и без дополнительных платных пользовательских метрик.

Расходы — $0 в рамках выбранного сценария.

**Secret Manager**

Предполагается использование одной активной версии секрета. При количестве операций чтения секретов, не превышающем бесплатную квоту, расходы составляют $0.

### 4.5. Сводная экономическая модель

| Сервис | MVP | Partners | Production |
|---|---:|---:|---:|
| Gemini API | $0.51 | $5.10 | $51.00 |
| Cloud Run | $0.00 | $0.00 | $10.08 |
| Firestore | — | $0.00 | $0.00 |
| Cloud Logging | — | $0.00 | $0.00 |
| Cloud Monitoring | — | — | $0.00 |
| Secret Manager | — | — | $0.00 |
| **Итого в месяц** | **$0.51** | **$5.10** | **$61.08** |

Для предварительного планирования бюджета дополнительно предусматривается резерв 20%:

| Этап | Расходы | Бюджет с резервом |
|---|---:|---:|
| MVP | $0.51 | $0.61 |
| Partners | $5.10 | $6.12 |
| Production | $61.08 | $73.30 |

Рассчитанная стоимость отражает выбранный сценарий, а не гарантированную стоимость эксплуатации.

В модель не включены расходы на разработку, поддержку, домен, дополнительные сетевые передачи, резервные копии и платные функции безопасности.

При росте количества AI-запросов или их средней длины стоимость Gemini API может увеличиться.

## 5. Обоснование выбранной архитектуры

Выбор Cloud Run обусловлен возможностью масштабирования приложения без управления серверами.

Firestore позволяет организовать хранение данных без развёртывания собственной базы данных.

Gemini API предоставляет доступ к готовой языковой модели, исключая необходимость обучения и эксплуатации собственной нейросети.

Cloud Logging и Cloud Monitoring необходимы для наблюдения за состоянием приложения и обнаружения ошибок.

Secret Manager обеспечивает безопасное хранение конфиденциальных данных.

Важное преимущество выбранного решения — постепенное развитие архитектуры. Вместо полного изменения технологического стека при увеличении нагрузки используются новые возможности существующих сервисов.

При этом самый дешёвый вариант на старте не всегда оптимален для дальнейшего развития. Поэтому Cloud Run и Gemini API используются с первого этапа, а сервисы хранения и мониторинга добавляются по мере необходимости.

## 6. Вывод

В ходе лабораторной работы была разработана концепция AI-приложения AI English Helper, предназначенного для помощи в изучении английского языка.

Созданы три архитектурные схемы в draw.io: MVP, тестирование партнёрами и Production.

Для каждого этапа определены необходимые облачные сервисы, их назначение и предполагаемая нагрузка.

Выполнен ориентировочный расчёт ежемесячных расходов, который показал возможность запуска небольшого AI-приложения с минимальными затратами при использовании управляемых облачных сервисов.

Предложенная архитектура обладает возможностью масштабирования, не требует самостоятельного управления серверами и подходит для постепенного развития MVP в полноценный продукт.
